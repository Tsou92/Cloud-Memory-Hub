# 一次性链接与远程 MCP 接入验证

关联 FR-01、FR-02、FR-03、FR-05、FR-06、FR-07、FR-12、ENG-01；设计见
[ADR-0065](../adr/0065-one-link-remote-agent-onboarding.md)。状态：实现及分项验证完成中，尚非正式发行证明。

## 产品边界

NAS Docker 为主体。电脑默认添加已有 Agent 的远程 MCP 和 Skill，不需要独立图形 App，
不安装记忆核心或模型。用户已明确先完成功能、缺陷修复及使用体验；后台视觉风格留待后续指定。
本轮界面只调整接入顺序、状态和错误恢复，沿用原样式。

链接 10 分钟有效，首次领取在同一事务内创建设备、固定项目授权及来源；同一领取者可恢复
丢失的回执。客户端在发出 claim 前持久保存随机秘密，长期凭证不进入输出或 Skill。
远程 MCP 复用既有七工具、授权与业务接收，不新增 NAS outbox。

## 独立审查与修复

独立审查确认两个真实问题，并补确定性回归：

1. 原 `curl | sh` 复制命令在下载 404 且无正文时返回 0。改为先完整下载成功再执行。
   对页面实际生成的完整命令，404、断网、半截下载必须非零且不执行；安装器失败码继续传递。
   PowerShell 使用终止式下载错误和不含凭证的固定失败异常，须在真实 Windows CI 复验。
2. 配置提案基于旧文件生成，但保存计划时再次读取当前文件当作基准，可能覆盖安装期间
   用户的新修改。改为把提案所依据的原始快照一起传给计划；基准变化即拒绝写入。
   配置文件、Hermes `.env` 和 Skill 均有并发变化回归，保持其他现场和备份。

审查同时覆盖邀请事务／恢复不复活、MCP 每请求身份、管理员 cookie 不替代设备、来源及
权限撤销、前端未知 POST 和已知 ID 恢复。UI 的「已配对」只表示签发身份，不表示已安装或在线。

完整回归另暴露启动顺序问题：MCP 管理器的异步启动在治理恢复之后让出执行，Core 的
维护任务可能再次进入恢复，从而在服务报告启动完成时短暂处于未就绪。原有空库懒加载
测试可单独复现。将最终串行恢复放在传输启动之后，保留原就绪及失败关闭条件；
原测试、搜索准入、远程 MCP 和恢复隔离共 29 项通过。未放宽测试断言或初始化原生存储。

复跑进一步发现，直接把治理恢复嵌入 MCP TaskGroup 会把原启动错误包装为异常组，破坏
既有错误处理合同。传输资源现通过独立退出回调关闭，不将 Hub 错误注入传输 TaskGroup，
也不展平或吞掉 MCP 自身错误。13 项新增回归覆盖原异常身份、真实任务取消和传输退出
失败；修前 6 项失败、7 项通过，修后全部通过。与原 Chroma、搜索准入、远程 MCP、恢复
隔离合计 45 项通过；完整回归仍需使用此最终修复重跑。

该修复后的完整本机 Hub 回归已完成：2,261 项通过、6 项条件跳过，耗时 352.32 秒。
随后固定 `5d7a3fe` 镜像的本机及 NAS 原容器烟测分别通过；Docker 上下文遗漏安装资源
已补齐并用真实资源 COPY 检查证实。日常服务、原 HTTPS 入口和旧测试现场保持不变。

## 三系统 CI 暴露的接入问题

`5d7a3fe` 的[运行 42785537972](https://github.com/Tsou92/Cloud-Memory-Hub/actions/runs/42785537972)
真实执行了三个平台的安装检查。Ubuntu、macOS 的 PowerShell 下载 404／半截内容仍返回 0，
也使两项 quality 检查失败；这证明仅在单条 `irm` 上设置 Stop 不够。复制命令现改为在独立
脚本块内设置终止错误策略，既不修改用户外层设置，也不在下载失败后执行旧脚本变量。
回归继续实际执行生成的命令，并包含安装器失败，不能以字符串检查代替退出码验证。

Windows 另暴露测试默认 cp1252 读取 UTF-8 脚本的问题，测试已明确编码；实际私有目录 ACL
设置仍失败。新增仅针对合成空目录／空文件的 Windows ACL 往返检查，可记录有界、去标识
的错误分类，产品命令仍只返回固定错误，不增加凭证输出。此项尚在定位，不能称 Windows
已支持。POSIX 缺 Python 时的固定 uv／Python 下载路径在 Ubuntu 和 macOS CI 已实际通过。

随后在本机使用官方摘要校验的便携 PowerShell 7.6.9，实际运行公共页与网页生成的两处命令，
404、半截、完整下载和安装失败共 8 个场景全部通过，残留旧脚本未执行。带真实 PowerShell
的 `make check` 完整通过，105 项中 3 项平台条件跳过。

`048d698` 的[诊断运行 42786554254](https://github.com/Tsou92/Cloud-Memory-Hub/actions/runs/42786554254)
已验证 Windows 缺 Python 时的下载准备路径；ACL 错误确定发生在首个 `Get-Acl` 的模块加载，
尚未修改任何权限。PowerShell 7 启动 Python 后，子进程 Windows PowerShell 5.1 继承了不兼容
的 `PSModulePath`。按[微软官方说明](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath?view=powershell-7.3#starting-windows-powershell-from-powershell-7)，
配置器只从该子进程环境移除这一变量，让 Windows PowerShell 构造原生路径；父进程和系统
环境、ACL 规则、所有者／保护／ACE 核验均不变。独立审查和 35 项本机客户端测试通过，
Windows 实机 ACL 往返仍需修复后的 CI 结果，不能由 Mac 测试替代。
