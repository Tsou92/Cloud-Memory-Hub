# 治理记录基础与 SDK 删除／恢复探针

日期：2026-10-25。关联 FR-06、FR-10、FR-11、FR-13、ENG-01。架构与分步接线方案见 [ADR-0011](../adr/0011-governance-authority-and-offline-sync.md)。本记录不代表忘记、彻底删除或离线缓存功能已经完成。

## 实测决定了实现顺序

`make probe-sdk-governance` 使用已安装 SDK 2.0.5.dev3、真实本地 embedding 和合成记忆，分 seed／delete／restored 三个独立进程操作临时数据。快照／恢复只发生在前一进程退出后，复用 SDK 公共 snapshot 接口；没有直接复制仍在写入的数据库。

实际观察：SDK 删除链头成功并且该 ID 不再存在，但旧链节点重新有效、原始记录仍在、被删正文仍出现在修订历史。同样内容换新 ID 能精确导入。恢复删除前的快照后，被删链头又成为 active／is_latest。无关项目在各阶段保持存在。

报告为 `observed_gaps`，没有把这些结果改成产品删除通过。外部生成模型调用为零；相同内容重导入测试是精确导入，不声称测过真实 LLM 再提炼。快照与恢复各包含八个文件，私有报告和进程日志路径由 `.local/governance/sdk-probe-final.log` 输出，不进入 Git。

## 已实现的基础模块

`governance_journal.py` 只维护不含正文的治理意图和项目变更记录，保存 forget／purge 的区别。目标标识通过带密钥摘要隔离实例、项目和类型，不保存原文。项目序号与意图在同一 SQLite 事务内提交；客户端最高已见序号／摘要用于识别旧库恢复或同高度分叉。操作 UUID 重试一致，换意图则拒绝；不存在的记录库不会在正常打开时自动重建。

初始化和打开要求当前用户所有、0700 父目录和 0600 普通单链接文件。打开时验证绑定和全部摘要链，读取时验证连续页与锚点；分页同时限制条数和条目字节预算。密钥由调用方受控配置提供，不写入记录库。调用方仍须负责权限校验，模块本身不构成用户授权接口。

该模块还没有接入 Hub 启动、管理 API、SDK 提炼和客户端。它没有删除任何用户数据，也没有把保存意图的回执标成完成删除。当前 NAS 仍为已验证的 `dev-234244b`，本轮没有更改运行实例、SSH 或日常 Agent 设置。

## 检查结果

- 治理模块 21 项测试通过，包含六个并发写入者、重复操作、错误密钥／实例、软硬链接、权限、损坏、跨项目游标、分页预算和伪造模型对象。
- 真实子进程在插入意图后、更新项目序号前立即退出；重新打开后无半条记录，重试正常提交。
- 真实文件恢复旧副本时客户端较高水位被拒绝；在相同序号写入另一条合法操作形成分叉时，旧客户端摘要也被拒绝。
- 完整 Hub 回归 196 项通过；本轮只修改独立基础模块，后续定向复测仍为 21 项通过。
- 固定上游 snapshot、delete_complete、raw_public_api、history_recent_for_user 共 20 项通过；这些包括上游替身测试，不与本轮真实 SDK 探针混称。
- `make check` 的格式、静态检查、19 项工程门禁、文档与源码凭证扫描通过。

## 自审与下一步

NAS 候选模块单独验证：通过 `DOCKER_HOST=ssh://nas uv run --locked python -u scripts/probe_governance_journal_container.py`，把当前模块流式送入使用既有镜像的禁网临时容器，逐次启动 prepare／crash／recover 三个进程，共用本次随机创建的独立卷。进程中断后没有半条意图，旧副本恢复与同高度分叉均被检测，0600 权限保留；临时容器及卷已清理。日志为 `.local/governance/nas-journal.log`。这是 NAS 文件系统上的候选代码测试，不是已安装 Hub 的治理集成、断电恢复或完整删除验收。

架构、代码质量、测试路径和性能已自审，外部审查未运行。基础模块不是治理权威接线完成：下一步必须增加独立挂载与启动核对，接到读取／提炼的抑制边界，保存关联范围，再实现物理清理与恢复协调。其后发布一致快照和本地缓存。旧镜像在存在治理意图后如何禁止继续服务，也必须在接线阶段完成并实测。
