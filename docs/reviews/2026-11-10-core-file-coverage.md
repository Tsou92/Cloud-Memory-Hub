# Core 四域文件覆盖与停服激活验证

日期：2026-11-10。基线 `71f41bc`，关联 FR-10、FR-11、ENG-01、[ADR-0047](../adr/0047-core-file-coverage-and-physical-authority.md)。本步提高实际恢复要求，不改变完整删除、全部输出域、六客户端或 G1 退出条件。

## 实现与兼容边界

Core 日志使用真实原生工厂生成样例，复用既有严格 formatter/projector；完整严格 LF 行原样保留，其余为最大连续原字节块。分帧独立于输入 chunk，不根据伪时间戳或嵌套 JSON 猜测逻辑事件，不丢失无 LF 尾部、CR 或非法 UTF-8。Core 原始块预算独立于 SDK 单行限制，实际 4 MiB 原生日志可分类；超限拒绝完整扫描。

四域扫描复用现有安全文件遍历、预算、回读和原子替换，共根目录按真实设备/inode 枚举一次并合并白名单。Core 两域覆盖实际活动文件及 `.1/.2/.3`。轮转名称测试使用原生字节复制，不能当作真实轮转触发测试。

旧 authority 和 SDK manifest/verification canonical 保留不变。新增四域 manifest v3、verification v2，以及与实际执行库 UUID 签名绑定的主链 capability。Store、恢复图和统一 ExecutionBinding 从同一恢复快照读取所需覆盖；旧业务 completed 和旧文件 verified 不再自动满足四域要求。该 capability 不是独立防回滚证书；未来普通四域运行仍须硬要求它，缺项旧备份不能自动降级。

文件执行复用原引擎，强制持有真实 Hub/SDK/Core 组合维护窗口。租约与线程、实例和实际根目录绑定，在 Core 写者可能重启前撤销。Core 全为空或只有严格元数据时可形成四域回执，实际 Core 字节保持不变。缺少独立 Core 正文授权时，完整扫描在任何 stage 退休、进度写入或 SDK 替换前拒绝，现有 SDK 授权不会扩展成 Core 删除许可。

实际停服 CLI `activate-file-coverage --writers-stopped` 在三目录锁内前后验证实际 Authority、绑定、恢复图及外部 witness，仅新增覆盖 capability。它不创建/迁移执行库、不补写 witness、不清理文件、不启动服务。后置验证失败保留已经提高的要求，重试不重复写入；空执行库可以返回 pending=0，但正文仍可能存在，因此该数值不是清理完成证明。

代码分为 `3ac41cb`（签名覆盖与读取）、`ee0ba5f`（Core 分类/扫描/执行）、`913f746`（停服激活与组合探针）三笔提交。上游仍是原 23 个补丁，没有修改固定上游树或添加新的上游补丁。

## 失败反例与独立审查

已保留并修复三项真实反例：旧已完成 SDK 回执在提高要求后仍被视为无待办；verification 内部 inventory.profile 与外层 profile 不一致仍被接受；相同贡献者缓存导致第二份有效 MAC 的清单绕过 Core artifact 授权检查。修复后要求一致的覆盖版本，并对每份 manifest 单独检查域授权，缓存只复用贡献者解析结果。

分类器独立审查使用 3000 组固定种子数据和输入分块，与独立 byte-LF oracle 核对原字节、偏移、最大连续块和失败后不可复用；110 组自由字段负例未被误认严格。7 字节输入块的 256 KiB、1 MiB、4 MiB 检查耗时约 0.011、0.045、0.187 秒，未观察到平方增长；这不是整个服务性能达标证据。

独立执行审查使用真实原生 gate 和活跃 DiagnosticLog：进入、退出及重启写者回调窗口均拒绝旧 lease，有效 body 内可用。实际旧 SDK pass 中断留下 stage 后，提高到四域；单操作、联合恢复及新增 repair 共存均验证成功，旧贡献者/profile 保持冻结，先退休旧 pass 再生成四域证明。加入未授权 Core 正文时，两条入口均零业务行变化、零文件替换拒绝。

扫描独立 38 项、激活独立 16 项通过，额外实际 CLI 错误隐私检查未回显合成凭证。激活缺旧能力、绑定间隙、旧 schema、错 UUID、缺/坏 witness、真实跨进程锁冲突、后置验证失败及重试均有实测。完整普通服务继续拒绝 schema2，独立审查未报告阻断。

补充实际历史操作验证：用真实 Store1 创建 completed purge 后，遗漏该操作的 cleanup 迁移映射会精确拒绝且零改动；完整迁移保留业务 completed，同时为每个 purge 建立 pending cleanup。启用四域后 Binding、Store、恢复图均报告待处理；仅删除副本的 cleanup 行会在只读加载时返回 execution_tampered。schema2 要求全部 purge 与 cleanup 一一对应；v1 的旧观察结果不构成四域完成证明。

## 后续范围与回退

无请求 Core 正文的独立物理许可尚未启用。完整文件字节相同仍不证明来源相同；无来源恢复副本的长期重删授权，以及跨项目混合旧片段的删除决定仍待确认。已确认的同项目长句重导入“拒绝整条事件”规则不代替这两项授权。

Docker 宿主日志覆盖、完整迁移/审阅/续做入口与普通 HTTP 协调仍待实现，不能通过将 Core 正文或 Docker 日志排除来宣布完成。正式 schema2 运行门槛继续保持，六入口、双设备、离线传播、完整备份恢复和真实模型质量也尚未完成。

本步不升级 NAS 常驻实例。若对隔离实例执行过覆盖激活，不得手工删除 capability 或直接启动旧程序；只可在停服、保留完整现场的前提下使用兼容的新程序继续维护，或按已有独立备份恢复流程另行验证。仅新增要求不重写业务授权，也不能撤销已完成的删除规则。
