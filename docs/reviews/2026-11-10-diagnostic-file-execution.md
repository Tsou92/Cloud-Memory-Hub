# 诊断物理文件执行组件与停服只读维护验证

日期：2026-11-10。关联 FR-10、FR-11、ENG-01、[ADR-0043](../adr/0043-diagnostic-physical-execution.md)。本记录区分独立组件成功与产品执行入口；后者尚未启用。

## 实现与复用

- 复用固定上游 `b7d9f0e0f417eae30b192882f848b432484c20a6` 的日志后端、真实 emitter、原处理器及轮转，新增补丁 0024 的同步维护/重绑定；manifest 共 22 个补丁。原始及各前序冻结源码未改动。
- 复用原主治理签名、请求证书、准入日志和租约；只读 Authority/Admissions/Ingest 共用原校验算法，读取已提交 WAL，不补行、不回写 witness，写入口提前拒绝。
- 独立 ExecutionStore2 显式迁移原计划、增加签名绑定/精确授权/不可变父关联及 CAS 进度；旧 intent 不重签。实际文件组件登记后才创建同目录 stage，复查真实字节，逐文件替换并接管原日志流，失败保留 pending。
- 真实 CLI 在 create_hub/Uvicorn/SDK 启动前执行只读预览；候选不声称来源或正文已经审阅。普通服务仍使用旧执行器，遇新 capability 或 schema2 提交间隙明确拒绝启动。

## 已观察的源码与兼容性证据

最终 Hub 全量 **1397 通过、5 个可选后端跳过**（224.31 秒），无预期失败；首轮为 1388 通过，之后增加轮转/错误归类和完整探针回归。原生新增及相关回归 192 项通过，Core 39 项通过。只读相关 157 项、执行与清单 70 项、独立执行/gate/store 81 项是交叉重叠子集，不相加当作独立测试数。`make check`、独立组件审查和独立完整源码探针均通过；源码环境的 `--installed` 负例明确拒绝。

独立复核发现：正常日志轮转后，无 stage 的旧 verified 进度仍要求旧路径保留旧前缀，造成错误拒绝。已限定此前缀保护只适用于实际尚存 stage，真实原生反例修复后通过。旧 verified 进度、旧正文与新 strict 尾行共同恢复时，重新扫描并清理授权正文、保留新增尾行，原签名操作未新增或改写。

完整探针还发现，目录扫描 contextmanager 曾把 yield 内的实际替换失败误译成扫描不可用。现只转换扫描自身错误，执行错误由引擎固定归类；77 项执行/清单回归验证准确错误、文件描述符关闭与现场保留。真实子进程探针和对应测试通过：HTTP 接纳两个合成请求、旧 purge 完成、三种原生格式 6 条记录、两次只读 CLI（含迁移 capability 间隙）、独立 repair 意图、第二次 replace 故障、全新进程恢复、只恢复日志再清理、安全尾行保留与变字节拒绝。探针只返回两域执行证据，明确 `whole_purge_completed=false`。`--installed` 校验 Hub、SDK、Core 三包及每个恢复子进程，禁止把工作树源码混入安装验证。

实际旧安装镜像 `cloud-memory-hub:dev-8588581` 的治理日志读取器接受原 admissions capability，拒绝新增 execution capability，错误为 `governance_capability_invalid`；主链头不变。这是实际旧读取器验收，不等于完整旧 Compose/启动迁移验收。

验证期间新私有上游克隆缺少已有模型缓存，首轮相关测试 21 项失败；按官方摘要校验并复用前序已验证的 5 个模型资源后完整回归通过，无外部模型调用、无网络下载或产品断言放宽。旧镜像读取器探针的入口/解释器两次启动错误也保留为失败记录，修正验证命令后才计通过。

## 交付边界

当前只在明确合成授权下验证 SDK 两域实际执行。文件组件返回 verified receipt，不调用主 purge complete；全部副作用域、Core 旧多行、Docker 历史输出、其他未知写者仍未闭合。产品物理确认、旧父操作与 repair 的完整恢复协调仍待接线。跨项目混合旧记录无法可靠分离时的处理方式仍待用户选择，不能从防重导入的整事件拒绝决定推导授权。
