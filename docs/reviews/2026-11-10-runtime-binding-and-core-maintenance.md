# 执行库统一读取、停服审阅与 Core 日志维护验证

日期：2026-11-10。基线 `9311e53`；关联 FR-10、FR-11、ENG-01、[ADR-0046](../adr/0046-governance-runtime-and-output-coverage.md)。本轮属于正式恢复接线的连续实施，不改变完整输出覆盖、维护入口和 G1 的退出条件。

## 已实现与复用

统一 ExecutionBinding 复用两个已存在 Store 的真实签名快照。Authority、应用抑制读取和 Executor 共享版本选择，缺库冷启动不创建执行库，迁移间隙或错 binding 不自动升级/回退。业务规则从同一快照读取 intent 和 records，排除 repair、保留孤立普通计划在丢弃前的抑制；Authority 将 cleanup.pending、orphan 和缺计划主意图列入待完成。普通 schema2 运行门槛继续保留。

真实旧行为反例中，在合法父业务操作后添加已签 repair 或孤立 repair，会使无关内容返回 content_rules_unavailable；修复后的业务规则只含真实父选择，原旧业务缺证明仍拒绝。应用组合验证使用实际 create_hub、HTTP、SQLite 与 SDK，未用伪造完成回执绕过运行限制。

新增停服审阅与签署组件复用原分类器、扫描、主日志、Store2 和三目录租约。审阅视图绑定全部实际文件、副本和父关系，长期精确记录授权仍允许原样恢复及轮转。真实 PTY 逐条完整显示、明确选择并最终确认，才生成进程内批准对象；孤立布尔值、伪 TTY、修改后的批准、变化后的新提交均不能签署。已签请求在新进程按原指纹返回 signed/pending，不要求删除前的物理视图，也不声称整个 purge 完成。

独立审阅还发现并修复：隐私遮盖可能隐藏其他项目的正标记，必须先检查原始及原生解码字符串；全部 Unicode 转义会使中文无法阅读，现保留可打印中文并转义控制字符。含秘密的记录明确标示遮盖，不冒称原字节全文。正文不进入诊断日志、报告或持久审阅缓存。

合法旧临时文件与新增正文变体共存时，原审阅扫描会先拒绝临时文件，导致恢复需要新授权、审阅又无法提供新授权。真实失败后复用原 `_RecoveryCapture`，只读证明全部实际临时文件及正式保留前缀，并绑定其身份/摘要；候选正文仍不作为旧保留字节。未知临时文件、唯一副本、前缀冲突和确认前文件变化均零改动拒绝。

## 上游补丁 0025 与真实写者边界

仅追加一个补丁，保留原 22 个补丁不变。复用 SDK 现有 file lease 的 require_bound/suspend/adopt/verify_bound，把 Core 实际工厂产生的 RotatingFileHandler 纳入同一合同；未知 handler 继续拒绝。Core 自有队列先暂停全部相关资源，再等待真实 writer，之后才取得 native 文件门闩。等待期间不持 writer 可能使用的 policy/handler 锁；构造与 configure/reset 受独立维护状态约束，原默认 legacy 行为保留。

原 drop 计数旁路严格投影、reset/configure 忽略 close 失败、Hub 维护提前越过实际 Core 写入均有修前真实失败。独立审查又复现两项并修复：关闭旧对象能清掉失败保护；首个 writer 启动失败会漏暂停后面的资源。现在故障域状态独立于日志对象存活，全部资源先暂停，只有对应域成功维护才能恢复；无关目录维护不能清掉原故障。

Hub 现有诊断维护入口已实际调用组合 gate，原 SDK 文件替换流程继续复用。该改动证明写者排空/重绑定，不等于已经实现 Core 历史文件分类与物理删除；进程内故障域也不替代跨进程治理恢复。

## 必须继续完成

普通服务尚未启用 schema2。Core 历史物理记录/持久文件进度、Docker 宿主挑战绑定的实际覆盖、可达 CLI 的正式迁移/确认/续做与普通 HTTP 执行协调仍需一起接通。不能把 helper 可调用、TTY 组件成功或写者暂停当成正式功能已经上线。跨项目混合旧记录整条删除仍待用户决定；其余可严格归属和无正文的路径继续实现。NAS 常驻服务本轮不自动升级，完整产品及六入口目标保持不变。
