# ADR-0035：彻底删除的缓存清理与中断恢复

日期：2026-11-09。状态：已实现，本地、安装及 NAS 验证完成；见[记录](../reviews/2026-11-09-purge-cache-recovery.md)。关联 FR-10、FR-11；补充 [ADR-0032](0032-governance-execution.md)。本项独立于 [ADR-0034](0034-inflight-ingest-and-content-reimport.md) 的在途任务与内容匹配取舍。

## 证据与复用

在真实 SDK 的中断续做测试中增加 `get_write_outcome` 核验：执行前存在目标结果；在 `_sdk_side_tables` 故障、恢复并显示 completed 后，结果仍存在。原文回执先被删除，重试无法再由回执获得 request_id。仅扫描被删事实文本没有发现这个遗漏，因为结果缓存可能仅含 ID 或其他轮次的历史输入。

固定上游 b7d9f0e 的 `DurableWriteQueue` 已将 job_id 与唯一 idempotency_key 持久保存；`clear_terminal_payloads` 只替换正文，不删除这组身份。复用该权威对应关系和 `main_database` 读取，不新增任务库或清理身份表。继续复用 SDK delete、原生写入结果和 Hub 签名物理记录集合。

## 决策

1. 清理任何内容之前，从签名范围内的原文回执 ID 和输入快照所属回执 ID 定位请求。优先核对现有原文；即便原文已清除，也从 Core 持久队列的 job_id 定位 idempotency_key。验证实例、来源所属项目、设备，以及仍存在的回执与队列是否一致；无法证明则返回 governance_purge_request_unproven，保持未完成，不猜测或清除其他请求。
2. 输入快照属于后续请求时，同样清除该请求的 SDK 结果缓存，因为结果内也保存同一输入快照。后续请求自己的原文和产出仍按原确认范围保留。整个 SDK 结果行清除，不改写其不可变内容。
3. 顺序改为：定位请求 → SDK delete → 清理 Chroma 队列/修订历史/写入结果 → Hub 回执和快照 → VACUUM/核验。Core 身份映射始终保留，任意一步重做都能再次定位同一结果。
4. 缓存路径取自正在使用的原生 SQLite cache，而非猜测向量目录的相邻文件。未支持的缓存实现不静默降级。
5. 启动重放同时检查原文/快照、SDK 节点、修订历史、Chroma 写前队列及写入结果。仅恢复旧缓存而未恢复节点，也必须重新清理目标结果，不能因节点缺失而跳过。
6. 独特原文扫描进一步发现：已完成任务的队列正文尚未经过后台清理时，VACUUM 仍会保留正文。删除在 VACUUM 前复用 clear_terminal_payloads，直到终态正文清理完毕；不取消或改判非终态任务，ADR-0034 的在途清扫仍未完成。
7. 仅缓存恢复实测触发 Core 后台维护与 Hub 启动同时调用 resume，争抢独占区并导致启动失败。resume 用进程内异步锁串行，重放完成标志在同一锁内检查；这不替代 ADR-0034 的 claim 就绪协调。

## 兼容与边界

不更改数据库结构或治理意图，不重签历史记录。旧操作可通过原 Core 任务映射恢复；映射缺失或矛盾时拒绝宣称完成，需要可证明的备份资料。本实现依赖 Core 保留 job_id/idempotency_key；今后若引入队列行清理，必须先迁移这组清理依据。

这是 Hub 接纳请求的恢复依据，不将任意 SDK 直接写入纳入 Hub 原文合同。已取消/unknown 在途任务的处置、队列正文清除和换 ID 重导入继续由 ADR-0034 处理。HNSW 已接受限制不变，用户自行保存的旧导出副本不自动修改。

## 验收

真实 SDK/HTTP/SQLite 与合成提炼器：正常删除和两处中断续做后目标结果不存在；无关结果保留；删除早期原文时引用它的后续结果缓存被清除，范围外的后续原文和原始轮次保留，依赖被删历史的事实按确认范围删除；只恢复旧缓存后启动重新清除；缺失/跨项目身份映射失败关闭。执行工程门禁、相关上游回归、Hub 全量和安装/NAS 探针，逐项记录证据。

已完成顺序自审和独立代码审查。独立审查未发现本次新增阻断问题；仅恢复 history、仅恢复 Chroma 队列的分支目前主要由代码核查支持，独立集成回归仍可补强，不与已实测的仅缓存恢复混称。

## 2026-11-10：请求诊断表也属于定向清理范围

新增真实 SDK/HTTP 回归发现：`pipeline_logs_v2` 和 `memory_operations_v2` 的目标请求行可在 purge 返回 completed 后保留；只恢复这两类日志、没有恢复 write_outcomes 或任何节点时，启动也未清理它们。日志中可保存独立诊断内容，原文片段扫描不能替代按请求定位的完整性核验。

沿用本 ADR 已验证的 request_id 定位与原事务，统一维护三张请求缓存表的清理和存在检查清单。精确删除同一已确认请求的结果、流水日志和操作日志，仍保留其他请求；VACUUM 和文件/WAL 核验照常执行。无需改动数据库结构、治理意图、签名范围或队列状态。缺表/损坏仍按已有存储错误路径保留现场，不能当作无残留。

此修复不等于诊断文件或后台日志任务已完整覆盖。JSONL、进程输出及未收尾的后台写入需在 [ADR-0039](0039-sdk-write-effect-observation.md) 的完整副作用工作中另外定位和验证，不能从 SQLite 两表测试外推。原有首次删除、已完成请求重试、仅诊断缓存恢复均须保留无关行并清除目标行和可读文件页中的合成内容。
