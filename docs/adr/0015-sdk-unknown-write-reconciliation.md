# ADR-0015：SDK 未知写入的精确结果核对

日期：2026-10-26。关联 FR-02、FR-04、FR-10、FR-11、ENG-01。作为治理暂停和恢复的前置能力，沿用 [共享 SDK 准入](0014-shared-sdk-admission.md)。

## 复用调查与范围

固定上游已经具备 SDK `get_write_outcome`、bridge 读取封装、持久队列 `unknown_jobs`／`payload_for`／`resolve_unknown` 和周期核对调度。Core 的 SDK 权威分支仍直接跳过周期核对。`execute_job` 的 SDK 路径明确把队列 idempotency_key 传给 `process_sdk_job`，后者原样传给 SDK；这与旧 Evidence／task 路径的另派生请求 ID 不同，不能沿用 UnknownWriteJob 文档中的旧假设。

复用以上发现、读取、调度和状态机，仅为 Core 增加可选 SDK 核对回调，并扩展原 `resolve_unknown` 的可选 SDK 回执参数；不创建第二个队列，不重发模型调用，不迁移或新增表。Hub 的核对器使用现有只读 bridge 与冻结输入计算原 SDK 身份。

## 完成证明与状态转换

```text
周期发现 unknown -> 读取原冻结请求 -> 按精确 request_id 查询 SDK 持久结果
  -> 核对请求／用户／Agent／会话／操作类型／成功状态及结果引用
  -> 再核对治理权威 -> 原队列单事务保存完整回执并转 completed

缺失、非终态、失败、身份不符、结果损坏、引用无法核对 -> 保持 unknown，不重发
```

SDK 结果必须为 `succeeded`，result.success 必须为 true；顶层身份字段和结果 request_id 必须严格匹配。请求的 add／add_extracted 选择沿用上游冻结记录与输入模式判定。失败结果不能证明没有局部写入，所以不自动转 dead；结果不存在也不当作“未写入”。

chat／productivity 两条结果形态分别按固定 SDK 合同验证，所有声明的原始记录和记忆引用均需核对存在性及用户／Agent 归属；原始记录还应匹配会话。`add` 的 chat 单数 memory_id 是原始记录；`add_extracted` 的单数 memory_id 是语义记忆，不允许写入 raw_ids。普通完成路径也修正后一项分类。不让上游旧 `receipt_for_request` 的宽松兼容行为把缺失身份或遗漏引用变成已完成。复用它的底层 bridge 查询和 DTO，保留其原调用者行为。

productivity 的经验／事实在 `coding.sqlite3` 与 `coding_cv.sqlite3`，不在 SDK 公共 get 的主集合。结果不带 variant，重启后 `_coding_store` 又未初始化，因此不能依赖“上次使用的 store”。复用固定 SDK 的路径派生规则，以 SQLite 只读连接查询两个变体的身份字段；每个声明的 ID 必须在正确的表中唯一存在并匹配归属，不创建 writer、表、向量集合或调用模型。零产出必须具有显式空列表，不从缺失字段猜测。

核对仅接受冻结 input_records；缺失的旧输入不从可能已经变化的 Evidence 重新猜测。保留上游禁止自动恢复的写后权限核验错误，避免把持久化成功误作权限核验通过。单轮与单回执引用数均设预算。

保存回执与转 completed 在原队列同一事务中完成，必须仍为同一 unknown 行、相同 updated_at 和冻结请求；任务被重试、重新接纳或输入变化时不覆盖新状态。重复核对幂等，旧 worker 的迟到 settle 仍不能覆盖该终态。原始记录／记忆 ID 沿用已有 sdk_raw_ids_json／sdk_memory_ids_json。旧版本可以读取已完成回执，不需要降低治理权威版本。

## 并发、预算与错误

核对期间持有 bridge 的 exclusive_access，覆盖 SDK 查询及最后的队列回执提交；共享准入因此能等待这项核对退出。阻塞存储工作用上游已加入等待的线程调用，取消不让未完成的提交跑到屏障之外。治理在查询前与提交前检查，未执行治理意图仍按现有规则隔离。

每轮有固定处理预算，使用 unknown_jobs 的稳定游标轮换；没有结果的旧任务不能长期饿死后面的任务。发现和查询错误保留未知状态，只报告固定诊断和计数，不能输出请求正文、模型响应或凭证。无注入的上游 Core 保持原行为；不修改用户的模型、来源授权或提炼开关。

## 验收与自审

- 真实 SDK 结果库与内容存储中已有成功写入，但队列回执丢失：核对后保存完整 IDs，并可通过已有事件状态看到 completed；不调用写入接口重试。
- 缺失、running／unknown／failed、错项目／Agent／会话／操作、坏字段、缺失结果记录：保留 unknown。一个坏任务不阻止后续任务核对。
- 保存前行状态、更新时间或冻结输入改变：拒绝旧核对结果。重复核对、迟到 worker 和重启不覆盖已保存结果。
- 取消、SDK 查询失败及提交失败：不误报完成，不泄露正文，下一轮可重新核对。
- 真实 SDK 持久化／进程重启测试与模型替身明确区分；本地生成替身不算外部模型质量验收。
- 执行工程门禁、Hub 集成、原上游队列／bridge 与 SDK 结果库回归；安装和 NAS 证据另列。

范围审查保留上游调度与状态机，仅补已确认缺口。架构、代码质量、测试和性能按上述条目自审；不声称独立同行审查。完整队列暂停、治理计划和实际忘记／删除仍需继续接通，不能由本次核对代替。

同时发现：当前治理 inventory 与普通读取尚未覆盖以上 productivity 存储；上游 coding_trace 又只保留最近 100 次写入，不能承担长期原始历史。此次核对回执不会把这些功能算作通过。后续必须补全其读取、来源保留与治理关系；预览遇到该项目的 productivity 数据先明确拒绝不完整范围，仍不开放删除执行。
