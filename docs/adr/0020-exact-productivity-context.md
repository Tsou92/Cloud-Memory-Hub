# ADR-0020：捕获实际历史输入与编程链写入标识

日期：2026-10-29。状态：接受；捕获与持久适配已验证，完整链观察待实现。关联 FR-02、FR-08、FR-09、FR-10、FR-11；延续 ADR-0018、0019。

## 复用调查

固定 SDK 的 CodingMemoryStore 从共享 trace 查询最近记录，再按最近 K 个 user-turn 保留消息尾部。单条文本截断保持消息数量与顺序，因此可以在同一次查询中携带每条消息所属 request_id，按实际窗口保留对应标识，不按文本去重或反查相似内容。CodingWriter 已把实际 history_messages 交给 extractor；在该调用点把标识加入原有持久 write_outcome。

HyCodeMem._add_round 已拿到更新行的 ID，插入游标也提供新 ID。observe 只需收集本次确实提交的 round IDs，不新增链库、队列或另一套 diff 分析。相同原话合并到旧行时仍返回被更新的原行 ID，多 hunk 的重复 ID 去重。client 已将 chain_rounds 写入结果，继续复用这个结果提交路径。

## 捕获与兼容性

新增历史请求标识字段，空列表表示实际没有使用历史；旧结果缺少字段则表示未捕获，不能推断为空。编程链另返回显式 complete／unavailable 状态与 round IDs，只有写入提交后才能给出 complete。链出错时回滚未提交事务，不能把部分写入当作零产出；原 SDK 的成功记忆结果及“不盲目重发模型”约束保持不变。

上游方法保留既有返回值；新增可选收集参数，默认调用兼容。SDK 结果是加字段而非替换既有字段，仍由已有持久结果库保存。新字段不能作为用户提供的权限证明，Hub 必须核对实际链行／线程归属和归档请求身份。

```text
真实 trace 查询 -> 每条消息的请求 ID -> 原窗口／截断 -> 实际 extractor 输入
                                                        -> 持久结果中的历史 ID
实际链 upsert -> 插入或更新的行 ID -> SQLite 提交 -> 持久结果中的链 ID
```

Hub 在现有配置数据库中增加独立版本标记 `cmh_context_schema=1` 和 `cmh_event_contexts`，保存规范化的历史请求、链轮次与捕获状态及摘要；不复制正文、不新增队列。上下文与原有输出关系在同一事务提交。每个历史请求必须映射到完整归档，并通过重建的 SDK 请求验证 user、agent、source；session 可以不同，符合固定 SDK 的实际历史窗口。找不到原文或跨域时保留未知状态，不重发模型。

历史原文是产出的输入父节点，不能作为本次的输出关系写入 `cmh_event_output_links`。显示来源和治理观察从持久上下文补充这些父节点；trace 清理、Core 队列回收和进程重开后仍使用长期 Event 归档。当前 Core 没有给 SDK 传 workspace_id，因此链行必须属于精确的 `user_id + "|"` owner；未来若改变调用参数，必须同步更新核验合同。

这次只保存并核对实际链行标识。完整链轮次、线程正文及仓库索引的治理观察继续保留未完成保护，不能凭存在行 ID 开放删除。普通聊天上下文与 reconciler 的候选输入也未完整捕获。

扩展表不改 lineage v1、Core 回执或现有输出摘要，旧版本可忽略这些附加表；旧版本期间的新写入没有上下文标记，升级后可从原 SDK 持久结果补充。旧 SDK 结果没有字段时明确保存 unobserved；unavailable 表示捕获失败；captured 加空列表才表示确实没有历史或链产出。旧数据缺口不能靠改摘要或重跑模型掩盖。已有 marker 或表形状不匹配时拒绝启动；已有上下文改变或损坏时拒绝接受，不静默覆盖。

## 工程自审与验收

架构只扩展现有观察和结果落盘点，不改模型选择、提炼内容或存储引擎。质量要求：正常路径不增加模型调用、不把请求标识注入模型正文、失败标记与空列表严格区分。性能增加与已选择消息／hunk 数量成正比的短标识列表，不额外扫描全库。

真实 SDK 存储测试覆盖窗口跨请求、一个请求多个 turn、重复内容不同请求、无 user 消息、空／损坏历史、上下文读取失败、零产出、两个变体共享历史、链插入／同轮合并／多 hunk、提交失败、项目 owner 隔离及持久结果重开。保留 SDK store、writer、场景路由、链和预处理回归。Hub 集成、安装及 NAS 证据另行记录，不把 SDK 捕获本身称为完整治理完成。

这是实现者架构、质量、测试和性能自审；顺序实施，不启动委派。完整普通聊天模型依赖、纠错、选择性治理执行、备份和恢复仍需继续交付；本设计不缩减这些要求。
