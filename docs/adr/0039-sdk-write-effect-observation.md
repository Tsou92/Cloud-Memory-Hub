# ADR-0039：在原生写入边界观察 SDK 副作用

日期：2026-11-10。状态：设计，分步实现。关联 FR-10、FR-11、ENG-01；承接 [ADR-0038](0038-durable-sdk-admission.md)。不改变已确认的整事件内容重导入拒绝规则。

## 问题与复用依据

固定上游 SDK 的成功结果只列业务返回的 ID，不是全部持久变更的清单。普通聊天的 shadow-only UPDATE、演化链折叠及画像旁路会修改返回清单之外的旧节点。生产力存储先提交 SQLite 再写向量；后者失败被捕获后可以 fallback 新建另一 ID，最终成功结果仍遗漏第一次落盘的行。零语义产出也可以留下 trace、chain、history 或缓存。

已有 `SdkReconciler`、`OutputLineage` 继续用于精确结果核对和来源关系，不能直接升级为完整副作用证书。既有 `MAY_INVOKE`、旧队列状态、结果缺失和终态清理签名也不能证明没有历史写入。需要记录真实持久化调用触及的对象，并最终把完整证据绑定到独立治理日志。

复用原生 Chroma 五个变更入口、HistoryStore 的共同插入点、SqliteCache 的请求日志入口，以及 SDK 的 claim/finish 和请求级派生任务收尾。不另建提炼器、队列、存储后端或模型调用。Chroma 在固定实现中不支持独立 tag/retrieval-clause 索引，必须显式说明这一能力边界，不能从空结果推断。其他后端和生产力路径不能自动继承 Chroma 的覆盖结论。

## 分步合同与兼容性

第一步增加**请求级原生变更观察**，只作为事实记录，尚不作为删除执行许可：

```text
SDK claim 新请求（缓存重放不再执行）
  -> 安装请求隔离的观察上下文（claim 是显式列出的前置持久写，不冒充已观察）
  -> 每个原生变更入口：记录 attempted selector -> 执行原操作 -> 记录返回或不确定
  -> 等待原有请求级派生任务收尾
  -> 将有界观察结果随原 write_outcome 保存
  -> 退出上下文；后续请求不能污染上一份结果
```

观察至少包含合同版本、请求身份、操作、明确覆盖的存储域、原生操作和稳定 selector、正常返回或不确定状态、超限/不支持原因。`returned` 只表示原函数正常返回，即使返回值为 false 也不能当作写入成功。只记录定位所需的 ID、类别和状态，不复制正文、模型输入或凭证。条目最多 1024、单字符串最多 512 UTF-8 字节、整体最多 256 KiB，整体按实际 JSON 转义后的字节计算；超限留下明确的不完整状态，不能截断后声称完整。批量写入在第一次原生 I/O 前记录全部可能触及的 ID，复用原生有效列表，不能为了观察额外消费一次调用者的迭代器。抛异常、取消或写成功后抛异常均不能从 attempted 清单中删除目标。

请求隔离在异步原生 facade 中建立，不能依赖线程池偶然传播上下文。复用 Python 的 [ContextVar](https://docs.python.org/3/library/contextvars.html)；线程池、后台日志 worker 不因同一调用链而自动获得覆盖承诺。上下文传入的派生任务必须沿既有生命周期结束。封闭返回深拷贝，不能悄悄追加到已返回或已序列化副本；内存对象后来失效也不能冒充能撤回已持久副本。因此第一步字段始终标为 `observation_only` 或 `incomplete`，不使用 `effects_complete`，未覆盖的诊断文件和不受生命周期管理的后台任务显式保留 `not_observed`。`sealed` 只表示这份观察已冻结，绝不表示之后不可能有写入。观察不改变原生算法、返回 ID 语义和异常传播。旧 outcome 没有此字段仍按旧合同读取，绝不补造历史观察。

第一步的上下文记录不独立抗崩溃：进程在持久回执前退出、只恢复旧 cache 或删除缓存时，记录可能缺失。因此即使观察状态封闭，也不叫“完整治理证书”，不解除当前在途执行拒绝，不改变数据库版本或启用旧任务取消。实现和测试必须明确区分这层事实与后续授权。

## 后续完整证明与成功执行

最终闭环必须同时具备：

1. 所有可达持久域的覆盖，包括失败 fallback、trace/chain、图的实体副本以及诊断日志；未覆盖域明确保留现场。
2. 真正写入前的持久定位记录，硬退出后仍能定位可能已写的对象；调用后汇总不能替代这一点。
3. 请求/birth/实际输入及 writer 能力版本绑定；目标当前状态区分相同版本、已证明清理后缺失、不同版本。不能只凭同 ID 同 owner 删除已改写记录。
4. 复用独立 admissions 文件、签名链/见证和 SDK 独占，在清理 cache/lineage 之前保存不含正文的不可变覆盖证书。旧请求没有真实证据时不得追溯补签。
5. 清单进入治理预览及签名范围；发现额外共享影响要求重新预览。completed 重放只能处理原签名对象，不能随恢复扩张范围。
6. 使用原 Core 精确 CAS 完成已证明任务的终止/恢复，绝不通过重新运行生成来核对旧写入。

引入有执行权限的持久证书时，另行升级主治理能力门、身份库与准入存储，测试实际旧镜像和分别恢复的混配。仅本次只读观察字段不触发迁移。当前普通治理路径的既有签名范围、缺证拒绝和生产力种类保护保持原合同。

## 架构、质量与性能评审

架构：一个请求上下文复用原生变更入口，避免在每个 writer 分支重复推断。原生存储拥有事实，Hub 拥有权限和治理签名，二者不能互相冒充。已有派生任务收尾优先复用。

质量：所有入口使用共同预算、记录与异常处理；业务函数不拼装任意证书字典。默认旧调用及重放合同必须保留。补丁单独审查、固定摘要，原上游目录保留不改。

性能：观察应随实际 mutation 数线性增长且严格有界，不为每次写入扫描全库。不得在观察层增加模型调用或重复全文读取。测试记录单请求对象预算及并发隔离；尚不据此宣称一分钟产品目标达标。

## 验收与失败矩阵

| 场景 | 预期证据 |
| --- | --- |
| 实际 chat add / add_extracted | 原生非空写入可观察，SDK 重新打开后 outcome 保留相同观察 |
| shadow-only / supersede / 画像旁路 | 业务返回清单之外的旧节点也有 attempted selector |
| 写成功后异常、取消、批量部分写入 | 不丢可能落盘目标，不将异常解释为零副作用 |
| 历史及缓存 | 按真实 memory_id/request_id 定位，未记录域不默认为空 |
| 并发、嵌套、重复请求 | 不串请求；缓存重放不再次写入或制造新观察 |
| 超预算、未知后端/域、迟到写入 | 明确不完整；不把部分清单用于治理许可 |
| 旧结果/只恢复旧 cache/硬退出 | 保留未知，不追溯补造完整证明 |
| 仅恢复旧 history | 已完成 purge 重放实际清理恢复的历史副本，签名范围和无关内容不变 |

测试复用已有真实 Chroma/SQLite、SDK 重开、画像、派生任务和治理恢复 fixture。合成模型只控制提炼输出；不冒充真实模型质量、六客户端接续或 NAS 安装结果。对应上游回归、Hub 测试、`make check`、安装和 NAS 证据分别记录。

第一步暂不实现持久证书、全生产力域清扫和新的治理许可；这些是后续必做工作，不能以本观察层通过测试关闭 FR-10/FR-11。自动备份、客户端安装和 GitHub 发布仍由原路线图跟踪。

并行分工：原生观察补丁与独立 history-only 恢复测试互不修改同一模块；补丁完成后再做独立审查和运行验收。Hub 执行许可保持原边界。
