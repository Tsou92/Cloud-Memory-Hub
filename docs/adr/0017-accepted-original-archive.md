# ADR-0017：在接纳事务中长期保存过滤后的原文

日期：2026-10-28。状态：接受，实施中。关联 FR-02、FR-03、FR-07、FR-08、FR-09、FR-10、FR-11、ENG-01。

## 工程评审与现有实现

按 plan-eng-review 的架构、代码、测试、性能检查进行实现者自审；延续用户已授权的完整开发范围和普通实现选择，不作需求缩减。未运行独立同行／外部模型审查，不默认启动委派。

固定上游的 `DurableWriteQueue.clear_terminal_payloads` 会把终态正文换成摘要；SDK staging Evidence 也会在成功或重启时释放。`coding_trace` 保存的是预处理、截断后的最近 100 次轨迹。暂停队列清理不能恢复完整原始 Event，也把处理队列变成历史库；普通 SDK raw 不能证明覆盖所有工作／编程、失败和待处理记录。

复用 Hub 已有 `EventEnvelope.canonical_payload/payload_digest`、本地过滤、项目授权、接纳回执事务和 Core 队列。回执新增原文列，不新建处理队列、语义记忆库或向量索引；当前语义内容继续由 SDK 权威管理。此决定补充 ADR-0003 的原文边界：SDK 保存其原生记录，Hub 接纳账本保存上传时的完整过滤后记录，两者不是彼此的无损副本。

## 数据流与协议

```text
过滤后的 Event → 校验权限／过滤版本／身份
                   ↓
配置库事务 → Core 幂等 submit → 回执 + 完整 Event JSON → COMMIT → accepted
                   ↓                    ↓
               SDK 提炼             history:list/get
                   ↓                    ↓
             临时队列正文清理      不受提炼／清理／重启影响
```

现有两个数据库不是分布式事务：queue submit 后、回执提交前崩溃，客户端尚未得到 accepted，应重发同一事件。重发复用相同队列任务，再原子保存回执和原文。若回执提交后响应丢失，重试核对 digest 与原文，不重复创建。不得在 accepted 回执中只保存摘要。

`cmh_ingest_schema` 升为 2（设备身份库仍为版本 2，远程协议仍为 v1）。`cmh_event_receipts` 增加 `payload_json TEXT NOT NULL`；原文和既有身份／摘要一起不可变保存。新增 scope 和 receipt_id 索引以支持权限内分页与详情。正文含凭证的事件仍在提交前拒绝，响应仍全文过滤后分块。

上传原文以 `cmhe:<receipt UUID>` 加入已有 history 接口，内容为完整 Event JSON；必须持有 history:read，只有 memory:read 不能获取正文。列表先按回执的接纳顺序倒序，再列 SDK 原生 raw，仍为实时分段分页。两类记录用途不同，SDK 原生 raw 可能与上传原文内容重叠，不将其声称为全局去重视图。原文 ID 不能被当成语义 memory ID。

提炼尚未完成、失败或来源停止写入，都不自动删除已接纳原文。忘记需继续允许用户主动历史查阅；彻底删除必须涵盖该列、SQLite WAL／备份、回执与所有派生关系。现阶段治理意图继续隔离整个实例，不能绕过既有治理保护读回原文。

## 兼容与恢复

新实例直接创建接纳 schema 2。旧 schema 1 不在 serve 时自动迁移，须停服、备份三卷和配置后执行 `migrate-originals --writers-stopped`，并持有现有进程存储租约。

迁移按冻结的 WriteRequest 反解完整 Event，并重新生成 write_request 及 Event digest，与旧回执逐项比对。消息内部可含来源标记，反解只接受末尾由上传边界追加的标记，最终以 digest 和全部冻结输入一致性证明，不能凭格式猜测恢复。如果旧队列已清理、数据缺失／不一致，整次迁移回滚并报错；不填写空正文，不宣称旧原文可恢复。配置库版本与所有回填在一个事务提交。

旧 Hub 在启动 Core 和清理队列前会拒绝 schema 2，禁止直接回退到不保存原文的镜像。没有下迁移。恢复旧完整备份仍必须通过独立治理权威检查，不能只恢复配置库或丢弃新治理记录来重新开放服务。

## 失败、测试与性能评审

| 路径 | 失败 | 预期验证／错误处理 |
| --- | --- | --- |
| 接纳事务 | 队列已提交、原文提交失败 | 无 accepted；重试复用任务并补完整原文 |
| 回执重放 | 原文被改、摘要或身份不符 | 固定错误，不成功确认损坏归档 |
| 历史读取 | 越权、读取期间撤销、非法 ID | 404／403／409，不泄露其他项目 |
| 生命周期 | 成功清理、失败、来源撤销、重启 | 归档仍可由授权用户完整读取 |
| 迁移 | 已清理正文、未知版本、部分损坏 | 原子回滚，旧版本和数据保留 |
| 维护 | 服务仍持有租约 | 拒绝迁移，不删除锁文件 |
| 治理 | 有未执行治理意图 | 延续实例隔离，不新增旁路 |

分页仅取当前页正文，计数与条件使用索引；迁移逐行验证，不把全部历史载入内存。原文增长是长期保留需求的结果；接纳仍受原有请求大小和队列磁盘余量保护。NAS 配置卷从仅配置扩展为包含敏感过滤后历史，必须与 data/governance 一同备份与治理。

## 实施顺序和后续

顺序实施：接纳 schema／迁移 → 原文读取 → 故障、重启、旧版本拒绝测试 → Linux／NAS 迁移与安装验证。主要修改共享接纳／读取模块，不并行委派。

本变更不新增 API、Agent 适配器或处理队列。完整来源链接（typed SDK output → archived Event）、原始版本与纠错关系、选择性治理执行及自动备份仍在原项目范围中继续实现，不能用原文存在代替这些验收。本轮不实施这些依赖后续关系清单的能力；继续在 roadmap 跟踪，不另建重复 TODO 清单。
