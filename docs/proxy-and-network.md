# 有代理时如何连接 Cloud Memory Hub

先保留原来的 Clash、Shadowrocket 或其他代理配置。Hub 需要直连还是经过代理，取决于你的服务地址：局域网、Tailscale 上的 NAS 通常直连；外网服务可能需要代理。安装检查会区分可用路径，不能把“配置已经写入”当成 Agent 已经连通。

## 先确定自己的服务地址

从 NAS 管理页复制 HTTPS 地址。例如 `https://hub.example.com:8443`：域名是 `hub.example.com`，端口是 `8443`。下面的 `hub.example.com` 都要换成自己的域名，规则中不包含 `https://`、端口、路径、一次性链接或密钥。

1. 确认 NAS 正在运行。如果地址来自 Tailscale，两端都要先连接同一个 Tailscale 网络。
2. 在出问题的电脑上打开 `https://hub.example.com:8443/healthz`。正常会显示 `{"status":"ok"}`；端口沿用自己的地址。
3. 查看安装器提示的“当前网络路径”和“直连路径”结果。两条都不通时，先核对地址、网络、DNS 和 HTTPS 证书；不要反复生成配对链接。

如果提示 `network_action_required`，表示健康检查已发现可用的直连路径，但 Agent 当前的代理路径不可用。此时不会继续领取新身份或写入 MCP；先按提示添加规则，再重跑原安装命令。链接已过期时在 NAS 重新生成；已有领取进度不会因这次网络诊断被清空。

| 检查结果 | 下一步 |
| --- | --- |
| 当前环境和直连都可用 | 保留当前代理设置，重新加载 Agent 的 MCP。 |
| 直连可用，当前环境不可用 | 为这个 Hub 的精确域名添加直连规则；CLI 可能还需要下面的 `NO_PROXY`。 |
| 当前环境可用，直连不可用 | 保留可用的代理，不要把这个域名加入直连白名单；确认代理节点能访问此服务。 |
| 安装器可用，Agent 仍失败 | 两个进程可能使用不同环境。完全退出并重新启动 Agent，再检查代理软件连接记录和实际 MCP 状态。 |

## Clash / Mihomo：为 NAS 添加精确直连规则

仅在“直连可用”时操作。在正在生效的配置中添加：

```yaml
rules:
  - DOMAIN,hub.example.com,DIRECT
  # 后面保留原来的其他规则
```

已有 `rules:` 时，只新增一条 `DOMAIN`，不要再创建第二个 `rules:` 或覆盖整份配置。将它放在可能命中这个域名的广泛规则及最终规则之前，并确认当前使用规则模式。使用订阅时，把例外放到客户端支持的本地覆写／自定义规则中，防止下次订阅更新丢失。

保存并重新加载配置后，重新请求 Hub，在代理软件的连接记录中确认该精确域名命中 `DIRECT`。规则按从上到下的顺序匹配，`DOMAIN` 只匹配完整域名；参考 [Mihomo 路由规则](https://wiki.metacubex.one/config/rules/)。

## Shadowrocket：添加该服务的直连例外

在正在生效的配置中找到规则编辑或直连白名单，新增一条完整域名规则：

- 类型选择 `DOMAIN`／完整域名。
- 域名填写自己的 Hub 域名，例如 `hub.example.com`。
- 策略选择 `DIRECT`／直连。
- 放在其他可能覆盖它的规则之前，保存、应用配置并重新连接。

不同版本的菜单名称可能不同。确认使用按配置规则路由的模式，然后在连接记录中核对该域名实际使用直连。不要只导入一份规则却继续使用另一份配置。Shadowrocket 支持按域名及 IP 范围分流，见[开发者的 App Store 产品说明](https://apps.apple.com/app/id932747118)。

如果服务必须走代理，把这一条规则的策略改为已验证可访问该服务的节点或策略组，而不是关闭全部代理。不要直接复制别人的策略组名称。

## Claude 等终端 Agent：补充 NO_PROXY

先分清两个地址：Hub 地址是 NAS 的 HTTPS 服务地址；代理地址是代理软件显示的本地 HTTP／混合端口，例如 `http://127.0.0.1:7890`。不要把 Hub 的端口改成代理端口，也不要因为 Hub 使用 HTTPS，就把本地普通 HTTP 代理的地址擅自改成 `https://`。

连接器使用系统标准库的 HTTP／HTTPS 代理能力。如果只提供 SOCKS 端口，可在代理软件中启用兼容的 HTTP／混合端口后配置环境变量；不能启用时，为可直连的 Hub 设置精确白名单。必须经代理且没有兼容端口时，应先补齐该网络能力，安装器不会关闭证书校验或假报已连接。

终端中的 `http_proxy`／`https_proxy` 可能仍把 NAS 请求交给代理，即使浏览器可以打开 Hub。仅在直连已验证可用时，在启动 Agent 的同一终端执行：

```sh
export NO_PROXY="${NO_PROXY:+$NO_PROXY,}${no_proxy:+$no_proxy,}hub.example.com"
export no_proxy="$NO_PROXY"
```

这会保留原有条目和外网代理。随后重新启动 Agent。已经运行的进程不会自动读取新环境；只在另一个终端修改变量也不会影响它。

需要长期生效时，可让安装 Agent 按当前 shell 安全地保存精确域名例外，保留原配置并检查重复项。不要设置 `NO_PROXY=*`，也不要把全部 `.ts.net` 都排除。终端的变量不保证传入已打开的桌面客户端；桌面客户端优先使用上面的代理软件规则，并完全退出再重新打开。

## 最后确认是否真正可用

Claude Code 使用 `/mcp` 查看该 Hub 是否连接，并确认工具已经加载。其他客户端查看其 MCP 状态和工具列表。然后先让 Agent 调用 `memory_status`；成功后再保存一句测试内容，并在 Hub 的“历史原文”核对。

`ECONNRESET`、TLS 连接失败或长期“连接中”不表示记忆已经保存。没有确认成功时，不要改存到另一款记忆插件并当作 Hub 共享成功，也不要因为网络问题删除项目或重新签发设备身份。

证书验证失败时，应修复地址、证书或网络路径，不能通过关闭 HTTPS 验证解决。报告问题只需客户端名称、系统、诊断代码及两条路径的结果；不要发送一次性链接、管理员凭证、Authorization 或完整代理配置。
