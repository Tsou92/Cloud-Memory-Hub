# Cloud Memory Hub 需求说明

更新时间：2026-10-21
状态：本轮产品需求已确认并记录为 v0.1 基线；客户端能力与技术方案尚待验证。

2026-11-10 优先级补充：用户明确先完成最小可用版本，依次交付多设备多 Agent 实时共享 memory、通用 MCP／可安装 Skill 接入、基于共享记忆的 session handoff。完整治理、复杂恢复等系统性功能细节后期完善，不能继续作为所有可用入口的前置；以下完整需求保留，按阶段交付并准确标注未完成项。

2026-11-10 接入与交付补充：主体运行在 NAS Docker；Mac／PC 默认通过一条命令或给 Agent 一段指令安装 MCP 连接／Skill，再用一次性链接完成配对，不需要独立图形 App。先完成功能、缺陷修复和使用体验，后台 UI 视觉风格待用户在其他代码完成后指定；当前只改善影响使用的流程、提示和错误恢复。实施及兼容性见 [ADR-0065](adr/0065-one-link-remote-agent-onboarding.md)。

## 1. 目标

2026-11-10 安装易用性补充：普通用户默认在 NAS 启用 Docker 与 SSH，将连接信息和官方部署话术交给电脑端 Agent，由 Agent 复用发行包、Compose 与现有初始化流程完成安装并返回可访问的管理页面。无需 NAS 管理网页内置终端，也不要求用户手动执行 Docker 命令。首次登录和必要账户授权仍由用户在本机完成。镜像仓库的图形化拉取入口须以实际公开、匿名拉取及完整启动配置验证为准；未发布前不展示虚构的镜像名。

在不同电脑及 Agent 之间共享同一套可追溯的记忆。服务采用 Docker 部署在用户自己的 NAS 上。

部署前核对 NAS 的 CPU 架构、可用内存、持久存储、Docker／Compose 与 SSH 权限。当前发行镜像面向 Linux amd64；实际可用资源以目标机器检查为准，测试机器的硬件配置不作为最低要求或性能承诺。个人机器的容量、已用空间、网络地址及其他本机配置不进入公开需求说明。

NAS 环境验收应使用宿主实际的 Docker daemon／Compose 信息，不用容器内部的版本代替宿主。独立容器验证的方法与范围见 [NAS 运行记录](reviews/2026-10-23-nas-preflight.md)。

默认体验是：换设备或换 Agent 后，能够了解项目背景、已定方案、任务进度、失败尝试、当前问题及下一步，并继续工作。

同时保留按需追溯原始对话、关键操作及输出的能力。跨 Agent 原生会话的完整恢复不是必需条件。

## 2. 通用接入要求

Cloud Memory Hub 必须面向各类 Agent 提供通用、双向的接入接口，不能将支持范围固定为当前使用的几个产品。

- 写入方向：提交记录、贡献和更新记忆，保留来源信息。
- 读取方向：检索和调用相关记忆，追溯其依据。
- 扩展方式：新增 Agent 应通过连接配置或独立适配模块接入，不应要求重写核心服务。
- 新接入的 Agent 同样适用项目分层、凭证过滤、同步、纠错与删除规则。
- 通用接口不等于所有第三方客户端已经支持全自动接入；每个客户端的实际读写能力必须单独验证。

第一批需要适配的入口：

| 应用 | 用户实际使用入口 | 自动读写能力验证状态 |
| --- | --- | --- |
| Claude Code | CLI | 待验证 |
| Codex | 桌面客户端 | 待验证 |
| OpenCode | 终端 | 待验证 |
| Hermes | 终端 | 待验证 |
| Cherry Studio | 桌面客户端 | 待验证 |
| Open Design | 桌面客户端 | 待验证 |

用户明确提出的未来接入示例包括 Workbody、Trae、Cursor；这些只是扩展示例，不构成支持范围上限。

## 3. 自动化与共享范围

在用户允许的范围内，全自动完成采集、提炼、同步及相关记忆的调用，无须逐条确认。

记忆分层共享：

- 个人偏好、工作习惯、通用经验跨项目共享。
- 项目需求、决策和进度默认在对应项目中使用。
- 支持按需跨项目检索。
- 统一存储不代表每次向每个 Agent 注入全部记忆；实际调用应与当前任务相关。

## 4. 同步时效与已有对话

正常联网时，以一轮对话结束为起点，目标是在 1 分钟内让其他设备和 Agent 能用到这轮产生的新记忆。

- 新建对话自动获取相关记忆。
- 已经打开的对话，在同步完成后的下一轮交互中自动获取相关新记忆，无须重新创建对话或手动刷新。
- 不打断已经开始生成的回答。
- 以上是待实现和实测的验收目标，不能仅凭记录已上传就认定达标。

NAS 不可访问时：

- 两台 Mac 使用本地缓存继续读取已有记忆。
- 继续记录新增内容。
- 恢复连接后自动补同步、合并并处理冲突。
- 展示同步状态，区分本地待同步内容和已共享内容。

## 5. 隐私与外部模型

除密码、密钥、访问令牌、登录 Cookie 等隐私凭证外，其他纳入共享的内容均允许外部模型访问和处理，不额外设置项目级的本地处理限制。

凭证过滤应发生在本地采集阶段、上传 NAS 或发送外部模型之前。过滤效果需要通过专门样例验证，不能将未经验证的过滤机制视为已经满足要求。

这些规则针对 Cloud Memory Hub，不改变用户现有 Agent 自身使用模型的方式。

## 6. 历史导入、保留与纠错

- 首次启用时，导入两台 Mac 上各 Agent 的全部已有记忆和历史会话。
- 可以后台分批处理，并进行去重。
- 保留来源应用、时间和所属项目等信息。
- 原始对话、关键操作记录、提炼后的记忆均长期保留，直到用户主动删除。
- 支持查看、纠正和删除记忆。

冲突处理原则：

1. 用户的明确纠正优先。
2. 结合时间、来源与上下文判断当前有效内容，不单纯以最新记录覆盖旧记录。
3. 保留依据和变更历史。
4. 无法判断时标记冲突，仅在影响当前任务时向用户确认。

明确区分两种操作：

- **忘记**：停止自动调用相关记忆，禁止再次自动提炼；原始历史仍可由用户主动查阅。
- **彻底删除**：进一步清除 Hub 保存的相关记忆和原始内容，而不是仅将其隐藏或停止调用。

两种操作都需要将规则同步到各端；离线设备恢复连接后应应用这些规则。重新导入历史记录或恢复旧备份，不能使已经忘记或删除的内容自动重新生效。

2026-11-09 已确认的内容重导入规则：在同一项目内，任一消息经过 NFC 与空白规范化后达到 16 个字符，并与已忘记／删除内容完全相同时，拒绝整个事件。更换来源、会话或记录 ID 不绕过该规则；混合事件含有其他新内容也整条拒绝。此选择优先防止内容复活，原样重述或引用该长句也会被拒绝，具体身份与兼容性见 [ADR-0034](adr/0034-inflight-ingest-and-content-reimport.md)。

原 Agent 自身的会话文件，以及用户自行保存的导出副本，不自动修改。

2026-11-10 已确认的无来源 Core 日志恢复规则：删除后，若恢复出整个文件字节完全相同、但无法证明来源的副本，保留现场并暂停相关恢复，重新审阅授权后才可删除。该决定保留为后续完整治理实现要求，不因本轮 MVP 优先级调整而撤销。

## 7. 管理界面

提供完整的独立网页管理后台，同时支持通过 Agent 进行操作。

需要覆盖：

- 搜索与浏览记忆。
- 查看原始记录和来源依据。
- 修改、纠正记忆，并提供明确区分的“忘记”和“彻底删除”操作。
- 查看设备连接与同步状态。
- 查看同步失败原因。
- 在后台验证当前管理员凭证后修改登录凭证，修改后所有旧后台会话失效，已连接 Agent 保持连接。设计与兼容性见 [ADR-0067](adr/0067-administrator-credential-change.md)。
- 通过 Agent 查询、纠正、删除记忆和检查同步状态。

## 8. 备份、恢复与迁移

- 在 NAS 内自动、定期保存历史备份版本。
- 支持选择历史版本恢复和回滚。
- 同时提供手动完整导出、导入功能，由用户自行保存备份。
- 备份恢复及导入必须继续遵守已有的忘记、删除规则，不能因回滚而自动恢复这些内容的有效状态。
- 本地离线缓存承担继续工作的用途，不等同于独立的历史备份。

自动备份的周期、版本数量、恢复过程中的同步协调方式，以及导出格式，留待技术方案确定。

## 9. 网络与费用

安装与使用应兼容无代理及有代理环境。自动处理不了宿主或代理软件的路由差异时，必须明确显示尚未连通，并为当前服务提供完整的精确域名规则／白名单、重新加载与验证引导；不能只凭安装器直连成功报告 Agent 已可用。设计见 [ADR-0068](adr/0068-proxy-aware-agent-onboarding.md)。

网络方案需支持跨设备访问自托管 NAS。Tailscale HTTPS 已有实测记录；NAS 自带转发或其他私有网络方案仍需验证其对后台服务与 MCP 的适用性。

外部模型费用暂不设固定月度上限，先观察实际用量和效果，再决定预算。首次全量历史导入与日常运行分别估算和展示用量、费用。

模型提供商、具体模型和计费方式尚未选定。

## 10. 范围边界

- 本项目负责共享记忆、对话历史和必要的操作证据。
- 项目源码、文档等实际工作文件由 Git、NAS 文件同步等现有方式管理。
- 记忆中知道某个文件发生过修改，不代表对应设备已获取该文件。
- Hy-Memory 是待评估的候选基础；尚未确认它能够独立满足本草案的全部要求。
- 对纳入采集范围的图片、PDF、聊天附件、设计稿等非文字内容进行解析，将有用信息提炼为可检索记忆，并保留来源引用。
- 非文字内容的原始工作文件仍由现有方式管理，不因此扩大为工作文件同步服务。
- 非文字内容同样适用隐私凭证过滤要求。

## 11. 验收场景草案

以下是从已确认需求推导的验证场景，不代表功能已经实现。

| 场景 | 预期结果 |
| --- | --- |
| 跨设备、跨 Agent 接续 | 一端完成一轮工作后，另一端在时效目标内能说明背景、已定方案、当前进度和下一步，并可追溯依据。 |
| 已有对话更新 | 另一端无须重开对话，在同步完成后的下一轮交互中使用相关新记忆。 |
| 项目分层 | 个人偏好可跨项目使用；项目专属上下文默认限定在对应项目，跨项目检索按需发生。 |
| 原始记录追溯 | 能从提炼后的记忆定位到对应原始对话或关键操作证据。 |
| 非文字内容提炼 | 从纳入采集范围的图片、PDF、附件和设计稿样例中提炼有效信息，能检索并追溯来源，同时排除样例中的隐私凭证。 |
| 断网恢复 | 断网期间能读取缓存和记录内容，恢复连接后完成补同步，并正确处理重复及冲突。 |
| 历史导入 | 两台设备的已有记录可分批导入，来源可查，重复导入不产生重复记忆。 |
| 凭证过滤 | 预置的密码、密钥及令牌样例在上传与外部模型请求之前被排除。 |
| 纠错 | 用户明确纠正后，相关检索使用纠正后的内容，历史依据仍可追溯；未决冲突不被静默当作确定事实。 |
| 忘记 | 相关内容不再参与自动调用和重复提炼；用户仍能主动查看保留的原始历史，规则能传播到各端。 |
| 彻底删除 | Hub 保存的相关记忆和原始内容被清除，不只是隐藏；不修改原 Agent 的会话文件或用户自行保存的导出副本。 |
| 备份恢复 | NAS 历史版本能够恢复；完整导出后可导入并恢复记忆及其来源关系。 |
| 防止自动重新生效 | 离线设备重连、历史重新导入、旧备份恢复后，仍遵守忘记和删除规则。 |
| 扩展接入 | 通过独立适配方式接入额外 Agent，完成统一读写流程，验证核心服务未绑定首批客户端。 |

## 12. 待完成的技术验证

- 六种实际客户端的历史记录位置、格式、可用扩展接口，以及已有对话自动获取记忆的能力。
- NAS 的实际资源、Docker 环境、存储空间及可用网络连接方式。
- 两台设备上同一项目的识别、关联与不同本地路径的处理。
- 实际历史数据量、导入成本，以及 1 分钟目标的性能验证方法。
- 隐私凭证过滤的覆盖范围、失败处理及验证方法。
- 非文字内容的实际格式支持、解析方式、来源可访问性，以及对同步时效和模型费用的影响。
- 记忆存储、检索与同步的一致性，以及并发写入、离线重放和备份回滚后的处理。
- 忘记与彻底删除的传播、关联内容的清理范围、受控备份中的清理方式，以及恢复和重新导入时防止内容自动重新生效的机制。
- 通用接口与客户端适配器的边界，及候选开源项目能够复用的具体能力。

本轮关键产品选择已记录完毕。以上待验证项应通过技术调研和实际测试确认，不能将需求目标表述为已经具备的能力。

## 13. 工程与发布要求

- 用户要求严格遵循大型项目开发流程和规范，需求、架构、实现、测试、审查、迁移和发布均可追踪。
- 从开发开始就作为 Git 项目管理；项目完成后应能够上传 GitHub，并具备可复现构建、验证和发布说明。
- 必须优先复用 Hy-Memory / MemHub 已有功能、代码和相应测试，避免重复开发；新增或替换实现需提供具体缺口和理由。
- 发布仓库的归属、可见性和项目自身许可证尚未确定，不由“将来上传 GitHub”推断为立即公开发布。
- 具体流程见 [工程规范](engineering.md)，复用决策见 [ADR-0001](adr/0001-reuse-first.md)。
